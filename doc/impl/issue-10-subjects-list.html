2設計方針

なぜこの構成にするのかを先に理解しておくと、コードの意図が見えてくる。

アーキテクチャ全体像

データは「モックストア → Route Handler（API）→ API クライアント → 画面」の一方向で流れる。 画面（ブラウザ）は同一オリジンの /api/subjects を fetch するだけで、データの実体（今はメモリ配列、将来は PostgreSQL）を知らない。

画面（SubjectList）と API クライアントのインターフェース（fetchSubjects / deleteSubject）は変わらない。 lib/api/subjects.ts の接続先 URL を変えるだけで Phase 2 へ移行できる。

なぜ「Client Component で取得」なのか

Next.js では、まず Server Component で取得するのが基本だ。だが今回は Client Component から fetch する。理由は3つ。

  • このアプリの設計がそうなっている。 要件定義書 §7 のとおり、本番はブラウザが Spring Boot REST API を「直接呼び出し」、Auth.js の JWT を Authorization: Bearer で送る方式。Client 取得はこの将来像と一致し、Phase 2 への移行が最小になる。
  • 削除→一覧更新→トーストが「画面の状態」の話だから。 削除後にどの行を消すか、どのトーストを出すかは useState で持つのが素直。Client Component が適任。
  • 自分の Route Handler を Server Component から呼ぶのは公式に非推奨。 下記の引用のとおり、Server Component は「データ源から直接」取得すべきで、自前の API を経由すると余計な HTTP 往復が発生する。今回は API（モック）越しに取りたいので、Client 取得が筋が通る。
📖
Next.js 16 公式ドキュメントより（Backend for Frontend / Caveats） "Fetch data in Server Components directly from its source, not via Route Handlers. ... For Server Components rendered on demand, fetching from Route Handlers is slower due to the extra HTTP round trip ... However, fetching data client side might be necessary for ... frequently polled data. For these, use community libraries like swr or react-query."
→ 本イシューは「自前のモック API を介して取りたい」「削除のたびに最新化したい」ケースなので、Client 取得が適切。 まずは依存を増やさず useEffect + useState で実装し、必要になったら SWR への置き換えを検討する（§Phase 2 連携メモ参照）。

Route Handler を「モック API」にする仕組み

Route Handler は app/.../route.ts に GET / DELETE などの関数を export するだけで作れる、 Next.js 内蔵の API エンドポイントだ。これを Spring Boot の代役として使う。 データは lib/subjects/mockStore.ts のモジュールスコープの配列に持たせる。

⚠️
モックの限界（理解した上で使う） メモリ上の配列なので、開発サーバーを再起動するとデータは初期値に戻る。また本番のように複数プロセスで共有もされない。 Phase 1 の動作確認用と割り切る。Route Handler の GET は既定でキャッシュされない（Next.js 16 仕様）ため、配列の変更はそのまま反映される。

削除フローと状態管理

削除は「2段階（確認 → 実行）」。SubjectList は次の状態だけ持てばよい。

state型役割
subjectsSubject[]表示中の一覧。削除成功時にここから対象を除外する
loadingboolean初回取得中フラグ（「読み込み中…」表示）
errorstring | null取得失敗時のメッセージ
pendingDeleteSubject | null削除確認中の対象。null ＝ ダイアログ閉
deletingboolean削除 API 実行中フラグ（ボタン二度押し防止）
削除クリック→ setPendingDelete(対象)→ ダイアログ表示
削除する→ deleteSubject(id)→ 成功: 配列から除外＋成功トースト
→ deleteSubject(id)↘ 失敗: エラートースト（一覧は維持）

ポイント：データは subjects state が「真実」なので、削除後は setSubjects(prev => prev.filter(...)) で消すだけ。 Server Component を使っていないので router.refresh() は不要。

確認ダイアログのアクセシビリティ

確認ダイアログには window.confirm() という手軽な手もあるが、見た目を整えられず「モダン」ではない。 自前の ConfirmDialog を作り、最低限のアクセシビリティを付ける。

属性 / 挙動理由
role="dialog" + aria-modal="true"スクリーンリーダーに「いま操作すべきはこのダイアログ」と伝える
aria-labelledby / aria-describedby見出しと本文をダイアログの名前・説明として関連づける
ESC キーで閉じるキーボードだけでキャンセルできる（#8 の NavLinks と同じ useEffect パターン）
背景（バックドロップ）クリックで閉じるマウス操作での離脱を自然にする。削除実行中は無効化
実行中はボタンを disabled二重送信を防ぐ
💡
なぜ <dialog> 要素ではなく自前の <div> か HTML 標準の <dialog> も良い選択肢だが、テスト環境（jsdom）の showModal() 対応が不安定。 本手順書では open state で表示を制御する <div> 方式にし、Jest で確実にテストできるようにする。

ARIA 属性の詳細解説

role="dialog" など4つの属性は WAI-ARIA（Web Accessibility Initiative – Accessible Rich Internet Applications）という仕様の属性で、 スクリーンリーダーや支援技術に「この要素が何か・何と関係しているか」を伝える。通常の見た目には影響しない。

属性何を伝えるかこれがないと
role="dialog" 「このdivはダイアログ（モーダル）だ」と支援技術に明示する。
素のdivには意味論的な役割がないため、スクリーンリーダーは見出しや段落と区別できない		 スクリーンリーダーがダイアログと認識できず、単なるブロック要素として読み上げる
aria-modal="true" 「このダイアログが開いている間、背景（オーバーレイ外）のコンテンツには触れないこと」を支援技術に指示する スクリーンリーダーがオーバーレイの裏にある本文まで読み続けてしまう。true を付けることで「今操作すべき範囲はここだけ」と閉じてくれる
aria-labelledby={titleId} id={titleId} を持つ要素（<h2> のタイトル）がこのダイアログの名前であると関連づける。
ダイアログにフォーカスが移ったとき、スクリーンリーダーはそのテキストを「ダイアログの見出し」として読み上げる。
titleId は useId() で生成した一意な値（例: :r3:-title）		 ダイアログに名前がない状態になる（"dialog" とだけ読まれ、何のダイアログか分からない）
aria-describedby={descId} id={descId} を持つ要素（<p> の説明文）がこのダイアログの説明であると関連づける。
タイトルに続けて説明文を読み上げ、ユーザーが内容を理解してから操作できる。
descId は useId() で生成した一意な値（例: :r3:-desc）		 スクリーンリーダーが説明文を自動では読まない。ユーザーが手動でフォーカスを移動させて初めて内容が分かる
✅
useId() で ARIA ID の重複問題を解決済み 実装では useId() を使い、コンポーネントのインスタンスごとに異なる ID を生成している。 aria-labelledby / aria-describedby と対応する h2 / p の id が一致することが保証される。 詳しくは Step 6 の callout「useId() とは何か」を参照。

遷移先スタブと認証

「科目を追加」「編集」のリンク先（/subjects/new・/subjects/[id]/edit）は別イシューでまだ未実装。 Issue #8 手順書 §2.5 のとおり、未実装ルートへ遷移 → 404 → ブラウザ戻る でヘッダーのハイドレーションが壊れる不具合があるため、 中身が空でも「ルートとして存在する」スタブを置いておく。

🔒
認証は proxy.ts が既に担保している Issue #6 で作った frontend/proxy.ts の matcher は api/auth 以外の全パスを対象にしている。 つまり /api/subjects もログイン必須で守られている。 モックの Route Handler 側に追加の認証チェックを書く必要はない（Phase 2 で Spring Boot 側に JWT 検証を実装する）。

2
モックストア — lib/subjects/mockStore.ts

Phase 1 の仮データと、それを操作する関数を置く。テスト仕様書 §15 のフィクスチャーを初期値にする。

frontend/lib/subjects/mockStore.tsts 
import type { Subject } from '@/types/subject'

// Phase 1 の仮データ。Phase 2 で Spring Boot + PostgreSQL に置き換える。
// module スコープの配列なので、開発サーバーが起動している間だけ変更が保持される。
let subjects: Subject[] = [
  { id: '660e8400-e29b-41d4-a716-446655440001', name: 'Spring Boot', createdAt: '2026-01-10T00:00:00Z' },
  { id: '770e8400-e29b-41d4-a716-446655440002', name: 'Next.js',     createdAt: '2026-02-15T00:00:00Z' },
  { id: '880e8400-e29b-41d4-a716-446655440003', name: 'Zod',         createdAt: '2026-03-20T00:00:00Z' },
]

// 一覧を返す（コピーを返して、呼び出し側からの破壊的変更を防ぐ）
export function getAllSubjects(): Subject[] {
  return [...subjects]
}

// id で1件削除。削除できたら true、対象が無ければ false。
export function deleteSubjectById(id: string): boolean {
  const before = subjects.length
  subjects = subjects.filter((s) => s.id !== id)
  return subjects.length < before
}
🧭
この層が将来「Spring Boot を呼ぶ」あるいは「PostgreSQL を引く」に化ける場所。 画面はここを直接触らず、必ず Route Handler（Step 3・4）越しにアクセスする。
💡
耳寄り — なぜ return subjects ではなく return [...subjects] か subjects はこのモジュールが持つ「在庫の本体」。参照をそのまま返すと、受け取った側が list.push(...) や list.sort() をしただけで本体が書き換わってしまう。 削除は deleteSubjectById 経由でだけ行いたいので、コピー（[...subjects]）を返して本体を守る（＝カプセル化）。
  • 今回の唯一の呼び出し元は GET ハンドラの Response.json(...)（JSON 化するだけ）なので、return subjects でも実害はない。それでも「外に渡す配列はコピーして返す」は低コストで良い習慣。
  • [...subjects] は浅い（shallow）コピー。配列は新品でも、中の各オブジェクトは同じ参照のまま。そのため getAllSubjects()[0].name = 'x' のような変更は元にも届く点には注意（完全な防御ではない）。

4
DELETE ハンドラ — app/api/subjects/[id]/route.ts

DELETE /api/subjects/{id} を作る。成功は 204 No Content、対象が無ければ 404（API 仕様 §4.2・§3.1）。 [id] という名前のフォルダが「動的な URL の一部」になる。

frontend/app/api/subjects/[id]/route.tsts 
import { deleteSubjectById } from '@/lib/subjects/mockStore'

// DELETE /api/subjects/[id] — 科目を1件削除する
// Next.js 16 では params は Promise なので await して取り出す。
export async function DELETE(
  _request: Request,
  { params }: { params: Promise<{ id: string }> },
) {
  const { id } = await params
  const deleted = deleteSubjectById(id)

  if (!deleted) {
    return Response.json(
      { code: 'NOT_FOUND', message: '指定した科目が存在しません' },
      { status: 404 },
    )
  }

  // 204 はボディを持たない
  return new Response(null, { status: 204 })
}
⚠️
Next.js 16 の落とし穴：params は Promise 昔は { params }: { params: { id: string } } と直接書けたが、Next.js 15 以降は params が Promise になった。 必ず const { id } = await params と await する。
💡
耳寄り — なぜ _request を引数に書くのか（使っていないのに） JavaScript の関数引数は位置で渡される。Next.js は必ず DELETE(request, context) の順で呼ぶため、 第2引数の params を受け取るには、第1引数の request を先に宣言しなければならない。

第1引数を飛ばして第2引数だけ受け取る構文は存在しない。 
// ❌ これは書けない。第1引数を飛ばして第2引数だけ受け取る構文はない
export async function DELETE({ params }: ...) {}

// ✅ 第1引数を宣言した上で、第2引数を受け取る
export async function DELETE(_request: Request, { params }: ...) {}
先頭の _ は「型上は必要だが意図的に使わない」という TypeScript / ESLint の慣習。 _ なしで request と書くと「定義したのに未使用」という lint エラーが出るため、_ を付けて抑制する。
💡
耳寄り — Response.json() と new Response(null, ...) の使い分け 使い分けの基準は 「ボディがあるか・ないか」。
書き方ボディContent-Type使う場面
Response.json(data, init) 自動で JSON シリアライズ 自動で application/json JSON を返すとき（404 エラー含む）
new Response(null, { status: 204 }) なし（null） 付かない 204 などボディが存在してはいけないステータスのとき
Response.json() は静的ファクトリメソッド（内部で new している）。 new Response(null, ...) はコンストラクタを直接呼んでいる。 .json() に null を渡すと Content-Type: application/json が付いてしまうため、ボディなしのときはコンストラクタ直呼びが正解。

なぜ NextResponse ではなく Response か？
NextResponse は Response を継承した Next.js 独自クラスで、Cookie 操作（res.cookies.set()）など Next.js 固有の機能を追加している。しかし今回のような「JSON を返すだけ」「204 を返すだけ」のケースでは その機能は一切使わない。Next.js 16 のドキュメントのサンプルコードも、不要なときはネイティブの Response を使うパターンを推奨している。NextResponse を使わなければ import { NextResponse } from 'next/server' も不要になる。
💡
耳寄り — RouteContext ヘルパーで型安全に（応用） 現状は params の型を手書きしている。 
// 現状：自分で「id という文字列がある」と書く
{ params }: { params: Promise<{ id: string }> }

// RouteContext：パスを渡すと型が自動生成される（import 不要）
ctx: RouteContext<'/api/subjects/[id]'>
手書きの場合、フォルダ名を [subjectId] に変えても型の id はそのまま残りエラーにならない。 RouteContext を使うとパス文字列と params の型が連動するため、ズレたときに TypeScript がエラーを出してくれる。

ただし「初心者のうちはどちらでもよい」。フォルダ名を変える機会は少なく、動作も同じ。 「こういう書き方もある」程度に覚えておけば十分。

frontend/lib/api/subjects.tsts 
import type { Subject } from '@/types/subject'

// Phase 1: 同一オリジンの Next.js Route Handler（モック）を叩く。
// Phase 2: `${process.env.NEXT_PUBLIC_API_BASE_URL}/api/subjects` に変え、JWT を付ける。
const BASE = '/api/subjects'

// 科目一覧を取得する。signal を渡すと useEffect のクリーンアップ時にリクエストをキャンセルできる。
export async function fetchSubjects(signal?: AbortSignal): Promise<Subject[]> {
  // ブラウザの HTTP キャッシュを使わず毎回サーバーから取得する
  const res = await fetch(BASE, { cache: 'no-store', signal })
  if (!res.ok) {
    throw new Error(`科目一覧の取得に失敗しました (${res.status})`)
  }
  return res.json() as Promise<Subject[]>
}

// 科目を1件削除する
export async function deleteSubject(id: string): Promise<void> {
  const res = await fetch(`${BASE}/${id}`, { method: 'DELETE' })
  if (!res.ok) {
    throw new Error(`科目の削除に失敗しました (${res.status})`)
  }
}
🧪
res.ok は HTTP ステータスが 200〜299 のとき true。 それ以外（404・500 など）は Error を throw し、呼び出し側（画面）の catch でエラートーストにつなげる。 エラーメッセージはそのままトースト文言になる。

耳寄り — useId() とは何か、なぜ使うのか

useId() は React 18 で追加されたフックで、コンポーネントのインスタンスごとに一意な文字列 ID を生成する。 生成される値は :r0: :r1: のような形式で、同じコンポーネントが複数回マウントされても重複しない。

なぜ id="confirm-title" のような固定文字列を使ってはいけないのか

ARIA の aria-labelledby / aria-describedby は DOM 上の id で要素を特定する。 id はページ内で一意でなければならない。 固定文字列を使うと、同じコンポーネントが2つ以上存在したとき（例: 一覧画面で複数の削除ダイアログが隠れて存在する）に id が重複し、 スクリーンリーダーが誤った要素を読み上げる。 

// ❌ 固定 ID — 同じコンポーネントが複数あると id が重複する
<div aria-labelledby="confirm-title">
  <h2 id="confirm-title">...</h2>

// ✅ useId() — インスタンスごとに異なる ID が生成される
const id      = useId()          // 例: ":r3:"
const titleId = `${id}-title`     // 例: ":r3:-title"
<div aria-labelledby={titleId}>
  <h2 id={titleId}>...</h2>

なぜ crypto.randomUUID() や Math.random() ではないのか

ランダム値はサーバー（SSR）とブラウザで生成のたびに異なる値になる。React はサーバーで生成した HTML とブラウザで再レンダリングした結果を照合する（ハイドレーション）が、 id が一致しないと ハイドレーションエラー が発生する。 useId() はコンポーネントツリーの構造から決定的に値を導くため、サーバーとブラウザで同じ値が生成され、ハイドレーションが壊れない。

📖
ISO 文字列とは何か — そして言語の壁を越えられる理由 ISO 文字列とは、ISO 8601（国際標準化機構が定めた日時表記の規格）に従った文字列のこと。 "2026-01-10T00:00:00Z" という形式で、年月日・時分秒・タイムゾーン情報をひとつの文字列に収めている。
部分例意味
2026-01-10年月日ハイフン区切り
T区切り文字日付と時刻の境界を示す
00:00:00時分秒コロン区切り
ZタイムゾーンUTC（協定世界時）を意味する。+09:00 のようにオフセットで書くこともできる
Phase 1 では mockStore.ts から、本番では Spring Boot から
formatDate() が受け取る createdAt の出どころは、フェーズによって異なる。
フェーズ出どころ値の例
Phase 1（現在） lib/subjects/mockStore.ts の配列に直書きした文字列 "2026-01-10T00:00:00Z"
Phase 2（本番） Spring Boot が PostgreSQL の TIMESTAMP 型を JSON シリアライズした文字列 "2026-01-10T00:00:00Z"（同じ形式）
Spring Boot は TIMESTAMP カラムの値を JSON に変換するとき、自動で ISO 8601 形式の文字列にする。 そのため formatDate() 側は Phase 1 と Phase 2 で何も変える必要がない。

ISO 8601 が言語の壁を越えられる理由
Java（Spring Boot）も JavaScript（ブラウザ）も、ISO 8601 を解釈する仕組みを標準で持っている。
  • Java: LocalDateTime / Jackson は ISO 8601 を標準でシリアライズ・デシリアライズできる
  • JavaScript: new Date("2026-01-10T00:00:00Z") でそのまま Date オブジェクトになる
「どう書くか」を ISO 8601 という共通の規格で統一しているから、異なる言語・システム間でも追加の変換処理なしにデータをやりとりできる。Web API の日時フィールドに ISO 文字列が慣習的に使われているのはこのためだ。
💡
耳寄り — toLocaleDateString() とは何か Date オブジェクトのメソッドで、ロケール（地域・言語）に応じた日付文字列を返す。 第1引数にロケールコード、第2引数にオプションオブジェクトを渡す。
引数値意味
第1引数（ロケール） 'ja-JP' 日本語（日本）形式で整形する
year 'numeric' 年を数値で表示（例: 2026）
month '2-digit' 月を2桁ゼロ埋めで表示（例: 01）
day '2-digit' 日を2桁ゼロ埋めで表示（例: 10）
ロケールを変えると同じ Date オブジェクトから異なる文字列が得られる。 
const d = new Date('2026-01-10T00:00:00Z')

d.toLocaleDateString('ja-JP', { year: 'numeric', month: '2-digit', day: '2-digit' })
// → "2026/01/10"

d.toLocaleDateString('en-US', { year: 'numeric', month: '2-digit', day: '2-digit' })
// → "01/10/2026"

d.toLocaleDateString('de-DE', { year: 'numeric', month: '2-digit', day: '2-digit' })
// → "10.01.2026"
ISO 文字列を直接表示すると "2026-01-10T00:00:00Z" のまま見えてしまうが、 toLocaleDateString() を通すことで人間が読みやすい形式に変換できる。 これが formatDate() の役割。
💡
アンマウント対策：active フラグ vs AbortController（現在の実装） 取得の途中で画面を離れる（アンマウントする）と、解決後の setState が警告になる。これを防ぐ方法は2つある。
手法仕組み特徴
active フラグ クリーンアップ関数で active = false にし、if (active) で setState をガード リクエスト自体は飛び続ける。setState を呼ばないだけ
AbortController + signal（現在の実装） クリーンアップ関数で controller.abort() を呼び、リクエスト自体を中止する ネットワーク通信ごとキャンセルできるため、active フラグより優れている
現在の実装は AbortController を採用している。fetchSubjects が signal を受け取れる設計になっているため、クリーンアップ関数で controller.abort() を呼ぶだけでリクエストがキャンセルされる。

abort() が呼ばれると fetch は AbortError を throw するため、catch で AbortError を判定して無視している。 これを忘れると、正常なキャンセルなのにエラーメッセージが表示されてしまう。
💡
耳寄り — AbortController とは何か AbortController はブラウザ標準の Web API で、「中止命令を送る送信機」のようなオブジェクト。 new Date() や new Promise() と同じ感覚で使えるブラウザ／Node.js 標準のオブジェクトで、追加インストールは不要。

2つのパーツで成り立っている。
パーツ役割
controller.signal 中止信号の受信機。fetch に渡すと、fetch がこれを監視し続ける
controller.abort() 中止命令を発火するメソッド。signal を監視しているすべての処理に伝わる 
const controller = new AbortController()

// signal を fetch に渡しておく（監視開始）
fetch('/api/subjects', { signal: controller.signal })

// 必要になったら中止命令を送る
controller.abort()
// → fetch が AbortError を throw する
subjects.ts にキャンセル処理を書かなくていい理由
fetch は signal オプションを受け取ったとき、ブラウザが内部で自動的に監視処理を持つ。 controller.abort() が呼ばれると fetch 自身が通信を中断して AbortError を throw する。 そのため fetchSubjects(signal) 側では「受け取った signal を fetch に渡す」だけでよく、キャンセルの実装は一切不要。 
// fetch が内部でやっていること（概念的なイメージ）
signal.addEventListener('abort', () => {
  // 通信を中断して AbortError を throw する
})
この仕組みは fetch の仕様として標準で定められているので、ライブラリや追加実装は不要。
💡
耳寄り — なぜ catch (e: Error) と書けないのか コード中に e instanceof Error ? e.message : '読み込みに失敗しました' という書き方が登場する。 「最初から catch (e: Error) と型指定すればよいのでは？」と思うかもしれないが、TypeScript はこれをコンパイルエラーにする。 
// ❌ コンパイルエラー — catch の引数に Error 型は指定できない
} catch (e: Error) {}

// ✅ unknown か any しか書けない（省略すると unknown 扱い）
} catch (e: unknown) {}
} catch (e) {}
なぜこの制限があるのか
JavaScript では throw に何でも渡すことができる。 
throw new Error('メッセージ')  // Error オブジェクト
throw 'エラー文字列'            // 文字列
throw 404                      // 数値
throw { code: 'FAIL' }         // オブジェクト
これは JavaScript の設計が「型に対して緩い」ことの表れで、throw の対象を Error に限定する強制がない。 TypeScript はその現実を正直に反映し、catch で捕まえる値の型を unknown（何が来るかわからない）として扱う。

そのため instanceof Error で型を絞り込んでから .message を使う、という書き方が TypeScript の正攻法になっている。 実際には fetchSubjects 内で throw new Error(...) しているので Error 以外が来ることはほぼないが、 型システム上は「何でも来うる」ため、Error以外の何かが飛んできたときには汎用メッセージ '読み込みに失敗しました' で代替する。

  test('キャンセルすると削除されない', async () => {
    mockFetchSubjects.mockResolvedValue(SAMPLE)
    renderWithProviders()

    await clickDeleteButton(user, 'Spring Boot')
    await user.click(screen.getByRole('button', { name: 'キャンセル' }))

    expect(screen.queryByRole('dialog')).not.toBeInTheDocument()
    expect(mockDeleteSubject).not.toHaveBeenCalled()
    expect(screen.getByText('Spring Boot')).toBeInTheDocument()
  })

  test('削除確定で行が消え、成功トーストが出る', async () => {
    mockFetchSubjects.mockResolvedValue(SAMPLE)
    mockDeleteSubject.mockResolvedValue(undefined)
    renderWithProviders()

    await clickDeleteButton(user, 'Spring Boot')
    await user.click(screen.getByRole('button', { name: '削除する' }))

    await waitFor(() =>
      expect(screen.queryByText('Spring Boot')).not.toBeInTheDocument(),
    )
    expect(mockDeleteSubject).toHaveBeenCalledWith('id-1')
    expect(await screen.findByText('科目を削除しました')).toBeInTheDocument()
  })

  test('削除失敗でエラートーストが出て、行は残る', async () => {
    mockFetchSubjects.mockResolvedValue(SAMPLE)
    mockDeleteSubject.mockRejectedValue(new Error('科目の削除に失敗しました（500）'))
    renderWithProviders()

    await clickDeleteButton(user, 'Spring Boot')
    await user.click(screen.getByRole('button', { name: '削除する' }))

    expect(await screen.findByText('科目の削除に失敗しました（500）')).toBeInTheDocument()
    expect(screen.getByText('Spring Boot')).toBeInTheDocument()
  })

  test('取得失敗時にエラーメッセージを表示する', async () => {
    mockFetchSubjects.mockRejectedValue(new Error('科目一覧の取得に失敗しました（500）'))
    renderWithProviders()
    expect(
      await screen.findByText('科目一覧の取得に失敗しました（500）'),
    ).toBeInTheDocument()
  })
})
💡
テストのポイント userEvent.setup() は beforeEach で生成し同一インスタンスを使い回す。各テストで再生成すると clickDeleteButton と各テストのイベントキューが分離してしまう。

繰り返しパターンは clickDeleteButton ヘルパーに切り出す。削除ボタンを押す手順を関数化することで各テストが「何をテストするか」に集中できる。user を引数で受け取ることで同一イベントキューを共有する。

findBy* と getBy* の使い分け。findBy* は「現れるまで待つ」非同期版。useEffect 後に表示される要素には await findByText、既に表示済みなら getByText を使う。

7Phase 2 連携メモ — モックから Spring Boot へ

Phase 2 で Spring Boot の REST API ができたら、原則 lib/api/subjects.ts だけを直せば移行できる。 画面（SubjectList）・ダイアログ・テストは無変更で済む設計にしてある。

Phase 2 での lib/api/subjects.ts（イメージ）ts 
// 接続先を Spring Boot に変更し、JWT を Authorization に付ける
const BASE = `${process.env.NEXT_PUBLIC_API_BASE_URL}/api/subjects`

export async function fetchSubjects(token: string): Promise<Subject[]> {
  const res = await fetch(BASE, {
    cache: 'no-store',
    headers: { Authorization: `Bearer ${token}` },  // API 仕様 §2
  })
  if (!res.ok) throw new Error(`科目一覧の取得に失敗しました (${res.status})`)
  return res.json()
}
🔑
Phase 2 で検討すること
  • JWT の取得方法：Auth.js のセッションから raw トークンをどう取り出してブラウザの fetch に渡すか（クライアントに渡す方式の是非を含めて要検討）。
  • 不要になるファイル：lib/subjects/mockStore.ts とモックの Route Handler は削除（または Spring Boot 未起動時のフォールバックとして残す判断もあり）。
  • CORS：別オリジン（:8080）になるため、Spring Boot 側で CORS 設定が必要。
  • 取得の高度化：自動再取得やキャッシュが欲しくなったら SWR / React Query の導入を検討（公式も推奨）。
