Context + Provider パターンを使う理由

学習ログフォーム・科目フォーム・バッチ画面など、互いに無関係な複数のコンポーネントからトーストを発火する必要がある。 Prop で渡す方法では、全ての中間コンポーネントに onToast を引き回す「Props Drilling」が発生する。 React Context を使えば、useToast() を呼ぶだけでどこからでもアクセスできる。

Server Component と Client Component の境界

Next.js 16 公式ドキュメントによると、React Context は Server Component では直接使えない。 しかし Server Component の layout.tsx から Client Component の Provider を レンダリング することは問題ない。 children を <ToastProvider> に渡すことで、各ページは Server Component のまま維持される。

なぜそうなるのか — 3 つのポイント

💡
① SC と CC の根本的な違い SC（Server Component） はサーバーで動き、HTML を生成して終わる。useState や useContext は使えない。
CC（Client Component） はブラウザで動く。状態・イベントハンドラを持てる。
React Context は「ブラウザ上のコンポーネントツリーで値を共有する仕組み」なので、SC では使えない。
💡
② Provider を「レンダリングする」と「使う」は別のこと layout.tsx（SC）は <ToastProvider> タグを書いているだけ。Context を消費（use/useContext）しているわけではない。
「CC の ToastProvider で包んでね」という指示を出しているだけ。
ToastProvider の本体（useState・Context 値の提供）はブラウザで動く CC の仕事。
💡
③ children が SC のまま維持される理由 —「誰が中身を決めるか」 children の中身を決めているのは、<ToastProvider> を「書いた側」（layout.tsx = SC）。
ToastProvider は受け取った children を置くだけで、作り直さない。
// layout.tsx（SC）が書いていること
<ToastProvider>
  {children} ← SC が決めた中身。ToastProvider は作り直さない
</ToastProvider>
箱の比喩：ToastProvider は「箱（CC）」、中身は SC が詰める。ToastProvider は箱として機能するだけで、中身は SC のまま変わらない。
誰が・どこで動くか
Server Component
  • ✅ サーバーで HTML を生成する
  • ✅ CC を呼び出す（JSXタグを書く）
  • ❌ useState / useContext は使えない
  • ❌ イベントハンドラは持てない
Client Component
  • ✅ ブラウザで動く
  • ✅ useState / useContext が使える
  • ✅ イベントハンドラを持てる
  • ✅ 外から children を受け取れる
children の中身は誰が決める？
layout.tsx（SC）が <ToastProvider>{children}</ToastProvider> を書いた時点で中身は確定。
ToastProvider（CC）はその中身を「そのまま受け取って置く」だけ — 再生成しない。
❌ Before — Provider なし
// layout.tsx (Server Component)
export default function AppLayout({ children }) {
  return (
    <>
      <Header />
      <main>{children}</main>
    </>
  )
}
// → useToast() が呼べない
✅ After — Provider でラップ
// layout.tsx (Server Component)
export default function AppLayout({ children }) {
  return (
    <ToastProvider>
      <Header />
      <main>{children}</main>
      <Toaster />
    </ToastProvider>
  )
}
// children は Server Component のまま
📖
Next.js 公式ドキュメントより（Context Providers） "React context is not directly supported in Server Components. To use context, create a Client Component that accepts children and wraps the context provider. This Client Component can then be imported and rendered within a Server Component, allowing other Client Components throughout the application to consume the context."

アクセシビリティ設計 — aria-live

スクリーンリーダーは aria-live 領域に DOM の変化があった際のみ読み上げを行う。 トーストが追加されたとき、視覚に頼らずユーザーに通知できるよう設定する。

属性値理由
role="region" — 通知エリアをランドマークとして識別させる（スクリーンリーダーで「通知」と案内される）
aria-live "polite" 現在の読み上げが終わってから変化を読む。成功・情報トーストは割り込み不要
aria-label "通知" role="region" には必ずアクセシブルな名前が必要。テストの getByRole('region', { name: '通知' }) でも使う
aria-hidden （アイコン要素に） 装飾アイコンをスクリーンリーダーに読み上げさせない
⚠️
エラートーストの読み上げ優先度について 本実装では全トーストを aria-live="polite" で統一する。 WCAG 2.1 SC 4.1.3 では、エラーは aria-live="assertive"（即座に割り込み読み上げ）が望ましい。 個人利用アプリのスコープでは "polite" で許容範囲。 本番化する際は §Phase 4 連携メモ の改善案を参照。

自動消滅の実装

各 ToastItem のマウント時に useEffect で setTimeout を登録し、 3,000 ms 後に removeToast(id) を呼ぶ。 クリーンアップ関数で clearTimeout を必ず呼ぶこと（手動で閉じた場合のメモリリーク防止）。

自動消滅パターン tsx 
useEffect(() => {
  const timer = setTimeout(() => removeToast(toast.id), 3_000)
  return () => clearTimeout(timer)  // ← 手動クローズ時にタイマーをキャンセル
}, [toast.id, removeToast])

1
ToastContext.tsx — Context・Provider・フックの作成

トースト状態の管理とグローバルアクセスを担うファイル。React 19 の新 API を使う。

⚛️
React 19 の新 API を使う 2 つのポイント ① <Context value={...}> — 旧 <Context.Provider value={...}> は将来廃止予定。React 19 からは Provider を省略した短縮記法が使える。
② use(Context) — 旧 useContext(Context) の後継。if 文の中でも呼べる柔軟な API。
app/(protected)/_components/ToastContext.tsx tsx 
'use client'

import { createContext, useCallback, use, useState } from 'react'

export type ToastVariant = 'success' | 'error' | 'info'

export type Toast = {
  id:      string
  variant: ToastVariant
  message: string
}

type ToastContextValue = {
  toasts:      Toast[]
  addToast:    (message: string, variant?: ToastVariant) => void
  removeToast: (id: string) => void
}

const ToastContext = createContext<ToastContextValue | null>(null)

export function ToastProvider({ children }: { children: React.ReactNode }) {
  const [toasts, setToasts] = useState<Toast[]>([])

  const addToast = useCallback((message: string, variant: ToastVariant = 'info') => {
    const id = crypto.randomUUID()
    setToasts((prev) => [...prev, { id, variant, message }])
  }, [])

  const removeToast = useCallback((id: string) => {
    setToasts((prev) => prev.filter((t) => t.id !== id))
  }, [])

  // React 19: <Context value={...}> — .Provider を省略する新記法
  return (
    <ToastContext value={{ toasts, addToast, removeToast }}>
      {children}
    </ToastContext>
  )
}

export function useToast(): ToastContextValue {
  // React 19: use(Context) — useContext の後継 API
  const ctx = use(ToastContext)
  if (ctx === null) {
    throw new Error('useToast は ToastProvider の子コンポーネント内で使用してください')
  }
  return ctx
}

実装のポイント

  • addToast / removeToast を useCallback でメモ化 → 子コンポーネントの不要な再レンダリングを防ぐ（詳細は下記）
  • crypto.randomUUID() は Web 標準 API。jest-environment-jsdom v30（jsdom v26 搭載）で利用可能
  • createContext<T | null>(null) + useToast 内で null チェック → Provider 外での誤用を即座に検出

useCallback でなぜ再レンダリングを抑制できるのか

💡
前提：JavaScript の関数は毎回「別のオブジェクト」になる

コンポーネントが再レンダリングされるたびに、関数定義は新しいオブジェクトとして生成される。 中身のコードが同じでも、参照（メモリアドレス）は異なる。

JavaScript の参照等価性 js 
const a = () => {}
const b = () => {}
a === b  // false — 中身が同じでも別オブジェクト
💡
React の再レンダリング判定は ===（参照の同一性）で行う

子コンポーネントは props が変わったときに再レンダリングする。 React の比較は参照の同一性（===）なので、 中身が同じ関数でも別オブジェクトなら「変わった」と判定される。

useCallback なし vs あり
useCallback なし
再レンダリング発生
↓
addToast = 新しい関数
↓
子の props が === で変化
↓
子も再レンダリング
useCallback あり
再レンダリング発生
↓
addToast = 同じ関数参照
↓
子の props が === で同一
↓
子の再レンダリングをスキップ
⚠️
ただし React.memo との組み合わせが必要

useCallback 単体では効かない。 子コンポーネントが React.memo で包まれていて初めて意味を持つ。 React.memo は「前回と props が変わっていなければ再レンダリングしない」という最適化。

2 段構えのセット tsx 
// ① 親側：useCallback で参照を固定
const addToast = useCallback((message, variant) => { ... }, [])

// ② 子側：React.memo で「props が同じなら再レンダリングしない」
const StudyLogForm = React.memo(function StudyLogForm({ addToast }) {
  // React.memo なしだと useCallback の効果がない
  ...
})
React.memo なしの場合、親が再レンダリングされると問答無用で子も再レンダリングされるため、useCallback で参照を固定しても意味がない。
📖
useEffect の依存配列でも有効 React.memo と組み合わせる場面以外にも、子コンポーネントが addToast を useEffect の依存配列に入れているとき、参照が安定していれば Effect の不要な再実行を防げる。
useEffect の deps に関数を使う例 tsx 
useEffect(() => {
  fetchData().then(() => addToast('完了', 'success'))
}, [addToast])  // addToast の参照が安定 → Effect が毎回再実行されない
⚠️
なぜ <ToastContextValue | null> にするのか — Fail Fast パターン

toasts は空配列で初期化できるため、<ToastContextValue> と書いてダミーの初期値を渡すことも技術的には可能。 しかしそうすると addToast が「何もしない関数」になり、Provider 外で呼んでもエラーが出ない。

パターンProvider 外で addToast() を呼ぶと
createContext<ToastContextValue>({ addToast: () => {}, ... }) 何も起きない。エラーなし。トーストも出ない。サイレントな不具合
createContext<ToastContextValue | null>(null) 即座に throw new Error(...) → バグの場所がすぐわかる
「動くけど何も起きない」より「すぐ壊れてエラーが出る」方がバグの発見が早い。これを Fail Fast（早く失敗させる） と呼ぶ。 null を初期値にする意図は、Provider の外での誤使用を実行時に即検出するためのものであり、積極的な設計判断。

Toaster.tsx — コンテナとトーストアイテムの作成

画面固定コンテナ（アクセシビリティ属性付き）と、個別トーストアイテムを同一ファイルに実装する。

app/(protected)/_components/Toaster.tsx tsx 
'use client'

import { useEffect } from 'react'
import { FaCheck, FaExclamationCircle, FaInfoCircle, FaTimes } from 'react-icons/fa'

import { type Toast, type ToastVariant, useToast } from './ToastContext'

const DISMISS_MS = 3_000

const VARIANT_STYLES: Record<ToastVariant, string> = {
  success: 'border-green-500 text-green-800 bg-green-50',
  error:   'border-red-500   text-red-800   bg-red-50',
  info:    'border-blue-500  text-blue-800  bg-blue-50',
}

function VariantIcon({ variant }: { variant: ToastVariant }) {
  if (variant === 'success') return <FaCheck            className="h-4 w-4 shrink-0" aria-hidden />
  if (variant === 'error')   return <FaExclamationCircle className="h-4 w-4 shrink-0" aria-hidden />
  return                             <FaInfoCircle         className="h-4 w-4 shrink-0" aria-hidden />
}

// ファイル内プライベート — 外部に export しない
function ToastItem({ toast }: { toast: Toast }) {
  const { removeToast } = useToast()

  useEffect(() => {
    const timer = setTimeout(() => removeToast(toast.id), DISMISS_MS)
    return () => clearTimeout(timer)
  }, [toast.id, removeToast])

  return (
    <div
      className={`flex w-80 items-start gap-3 rounded-lg border-l-4 bg-white
        px-4 py-3 shadow-md text-sm ${VARIANT_STYLES[toast.variant]}`}
    >
      <VariantIcon variant={toast.variant} />
      <span className="flex-1">{toast.message}</span>
      <button
        type="button"
        aria-label="通知を閉じる"
        onClick={() => removeToast(toast.id)}
        className="ml-auto shrink-0 opacity-50 hover:opacity-100 transition-opacity"
      >
        <FaTimes className="h-3 w-3" aria-hidden />
      </button>
    </div>
  )
}

export default function Toaster() {
  const { toasts } = useToast()

  return (
    <div
      role="region"
      aria-live="polite"
      aria-label="通知"
      className="fixed right-4 top-4 z-50 flex flex-col gap-2"
    >
      {toasts.map((toast) => (
        <ToastItem key={toast.id} toast={toast} />
      ))}
    </div>
  )
}

実装のポイント

  • ToastItem はファイル内プライベート関数（export しない）。Toaster だけが外部向けインターフェース
  • fixed right-4 top-4 z-50 で画面右上に固定。DOM 順序は見た目に影響しない
  • アイコン要素に aria-hidden を付与し、スクリーンリーダーが「チェックマーク画像」などと読み上げるのを防ぐ
  • aria-label="通知を閉じる" はテストで getByRole('button', { name: '通知を閉じる' }) として参照する
  • const { removeToast } = useToast() — 戻り値オブジェクトから必要な関数だけを取り出す分割代入（詳細は下記）

useToast() の戻り値と分割代入

💡
const { removeToast } = useToast() と書く理由

useToast() の戻り値は関数単体ではなく、複数のプロパティを持つオブジェクト。 そのまま受け取っても関数として呼び出せないため、分割代入で必要なものだけ取り出す。

useToast() の戻り値 ts 
{
  toasts:      Toast[],        // トースト一覧
  addToast:    (...) => void,  // トースト追加
  removeToast: (...) => void,  // トースト削除 ← ToastItem が使うのはこれだけ
}
❌ 分割代入なし
const removeToast = useToast()
// removeToast = { toasts, addToast, removeToast }
// オブジェクト全体が入る → 関数として呼べない
removeToast(id)  // ❌ エラー
✅ 分割代入あり
const { removeToast } = useToast()
// removeToast = fn  ← 関数だけ取り出せた

removeToast(id)  // ✅ 呼べる

引数の分割代入と型定義の読み方

💡
{ variant }: { variant: ToastVariant } の読み方

コードに登場するこの記法は、分割代入（値の世界）と型定義（型の世界）が : を境に並んでいる。

{ variant } : { variant: ToastVariant }
値の世界（分割代入）

引数として受け取ったオブジェクトから
variant プロパティを取り出す。
関数内で variant と直接書ける。

型の世界（型定義）

variant というキーを持ち、
その型が ToastVariant であるオブジェクトを
引数として受け付けますよ、という宣言。

分割代入あり vs なし tsx 
// 分割代入あり（このコード）
function VariantIcon({ variant }: { variant: ToastVariant }) {
  // variant と直接使える
}

// 分割代入なし（同じ意味）
function VariantIcon(props: { variant: ToastVariant }) {
  // props.variant と書く必要がある
}

型定義のオブジェクト構文は必ず { キー名: 型 } の形で書く。 { ToastVariant } のように型名だけを書いても、それが何のキーの型なのか TypeScript には伝わらないため文法エラーになる。

key と toast を両方指定する理由

💡
2 つは目的が異なる

リスト描画で登場する key と toast は、見た目は似ているが役割が全く違う。

props誰が使うか目的
key={toast.id} React 内部 リストの各要素を識別する。ToastItem の中からは参照できない
toast={toast} ToastItem メッセージ・種類・ID を受け取り、表示に使う
Toaster.tsx — リスト描画部分 tsx 
{toasts.map((toast) => (
  <ToastItem
    key={toast.id}   // React が使う（ToastItem 内では参照不可）
    toast={toast}    // ToastItem が使う（中身を表示するため）
  />
))}

key が必要な理由は、React がリストを再レンダリングするとき「どの要素が追加・削除されたか」を判断するため。 key がないと全要素を作り直してしまい非効率になる。 toast.id を使うのは、各トーストに一意な値だから。

フェイクタイマーを使って自動消滅を同期的に検証する。

⏱
フェイクタイマーのパターン jest.useFakeTimers() で setTimeout を乗っ取り、 jest.advanceTimersByTime(3000) で時間を進める。 userEvent.setup({ advanceTimers: jest.advanceTimersByTime }) で ユーザーイベントとフェイクタイマーを連携させることが重要。 act() で React の状態更新をフラッシュしてから DOM を検証する。

Jest タイマー制御 API の役割

💡
なぜフェイクタイマーが必要か

トーストは「3秒後に消える」という挙動を持つ。テストで実際に 3 秒待つと テストが遅く・不安定になる。 Jest のフェイクタイマーを使えば、時間を手動で操作して即座に・確実にその挙動を検証できる。

API何をするかこのテストでの用途
jest.useFakeTimers() setTimeout などを Jest 製の偽物に差し替える。呼んだだけでは時間は進まない beforeEach で各テスト前に有効化
jest.runOnlyPendingTimers() 登録済みの setTimeout を今すぐ実行する。3000ms 待たずに「3秒が経過した」状態にできる afterEach で残留タイマーをクリーンアップ
jest.useRealTimers() 偽物のタイマーを本物に戻す afterEach でテスト後のクリーンアップ
フェイクタイマーの動作イメージ ts 
jest.useFakeTimers()
setTimeout(() => console.log('3秒後'), 3000)
// ← この時点ではまだ何も起きない

jest.runOnlyPendingTimers()
// → 即座に「3秒後」が出力される。実際には1msも経っていない

jest.useRealTimers()
// → タイマーを本物に戻す
💡
advanceTimersByTime と runOnlyPendingTimers の違い

どちらもタイマーを即時実行するが、「時間の概念があるかどうか」が異なる。

advanceTimersByTime(ms)runOnlyPendingTimers()
何を実行するか 指定ミリ秒以内に発火するタイマーだけ 現在登録されている全タイマー
時間の概念 あり（何ms 経過したかを指定） なし（遅延を無視して即実行）
主な用途 「3秒後に消える」などの時間依存の挙動を検証 テスト後の残留タイマーをまとめてクリーンアップ
使い分けの例 ts 
setTimeout(() => console.log('A'), 3000)
setTimeout(() => console.log('B'), 5000)

jest.advanceTimersByTime(3000)
// → 「A」だけ出力。「B」は 5000ms に達していないので発火しない

jest.runOnlyPendingTimers()
// → 残っている「B」も含めて全タイマーを即実行
✅ テスト本体で使う
// 「ちょうど3秒経った」を再現
act(() => jest.advanceTimersByTime(3_000))
expect(screen.queryByText('登録しました'))
  .not.toBeInTheDocument()
✅ afterEach で使う
// 残留タイマーを全部片付けてから
// 本物のタイマーに戻す
jest.runOnlyPendingTimers()
jest.useRealTimers()
⚠️
runOnlyPendingTimers() は act() で囲む

afterEach で jest.runOnlyPendingTimers() を呼ぶと、残っている setTimeout のコールバックが実行される。 このコールバックは removeToast() を呼ぶため、ToastProvider の state が更新される。この更新が act() の外で起きると React が警告を出す。

runOnlyPendingTimers() が state 更新につながる流れ
runOnlyPendingTimers()
→ setTimeout のコールバック実行
→ removeToast(id) 実行
→ setToasts(...) 実行 ← state 更新！
❌ act なし
afterEach(() => {
  jest.runOnlyPendingTimers()
  jest.useRealTimers()
})
// state 更新が act 外 → 警告
⚠️ 同期 act（不完全）
afterEach(() => {
  act(() =>
    jest.runOnlyPendingTimers())
  jest.useRealTimers()
})
// Promise が await されない
✅ 非同期 act（正解）
afterEach(async () => {
  await act(async () =>
    jest.runOnlyPendingTimers())
  jest.useRealTimers()
})

act() とは：「この処理の中で state が変わるよ」と React に伝える関数。 React 18 では state 更新が非同期で処理されるため、同期の act() では更新の完了を待てない。

await は非同期関数の中でしか使えないため、afterEach のコールバック自体も async () => {} にする必要がある。afterEach は async 関数を渡すと その Promise が解決するまで Jest が待ってくれる。

app/(protected)/_components/Toaster.test.tsx tsx 
import { act, render, screen } from '@testing-library/react'
import userEvent                from '@testing-library/user-event'

import Toaster                        from './Toaster'
import { ToastProvider, useToast } from './ToastContext'

// テスト用ヘルパー: Provider 内から addToast を発火するボタン
function TriggerButton({
  message,
  variant,
}: {
  message: string
  variant?: 'success' | 'error' | 'info'
}) {
  const { addToast } = useToast()
  return (
    <button type="button" onClick={() => addToast(message, variant)}>
      トースト追加
    </button>
  )
}

// Provider + Toaster をまとめた Wrapper
function Wrapper({ children }: { children: React.ReactNode }) {
  return (
    <ToastProvider>
      {children}
      <Toaster />
    </ToastProvider>
  )
}

describe('Toaster', () => {
  beforeEach(() => jest.useFakeTimers())
  afterEach(() => {
    act(() => jest.runOnlyPendingTimers())
    jest.useRealTimers()
  })

  test('addToast を呼ぶとトーストが表示される', async () => {
    const user = userEvent.setup({ advanceTimers: jest.advanceTimersByTime })
    render(
      <Wrapper>
        <TriggerButton message="登録しました" variant="success" />
      </Wrapper>,
    )
    await user.click(screen.getByRole('button', { name: 'トースト追加' }))
    expect(screen.getByText('登録しました')).toBeInTheDocument()
  })

  test('3 秒後に自動で消える', async () => {
    const user = userEvent.setup({ advanceTimers: jest.advanceTimersByTime })
    render(
      <Wrapper>
        <TriggerButton message="登録しました" variant="success" />
      </Wrapper>,
    )
    await user.click(screen.getByRole('button', { name: 'トースト追加' }))
    expect(screen.getByText('登録しました')).toBeInTheDocument()

    await act(async () => { jest.advanceTimersByTime(3_000) })
    expect(screen.queryByText('登録しました')).not.toBeInTheDocument()
  })
💡
await act(async () => { jest.advanceTimersByTime(3_000) }) の読み方

3 つのパーツに分解して読む。

await act(async () => { ... }) jest.advanceTimersByTime(3_000)
① await

act() が返す Promise を待つ。これがないと state 更新が終わる前に次の行に進んでしまう。

② act(async () => {})

「この中で React の state が変わるよ」と伝える。async にすることで再レンダリングなど非同期の処理が全部終わるまで待つ。

③ advanceTimersByTime

フェイクタイマーを 3 秒進める。これで setTimeout(removeToast, 3000) が発火する。

まとめると「タイマーを 3 秒進めて、それによる state 更新と再レンダリングが全部終わってから次のアサーションに進む」という 1 行。

（続き） tsx 

  test('複数のトーストを同時に表示できる', async () => {
    const user = userEvent.setup({ advanceTimers: jest.advanceTimersByTime })
    render(
      <Wrapper>
        <TriggerButton message="メッセージ" variant="info" />
      </Wrapper>,
    )
    await user.click(screen.getByRole('button', { name: 'トースト追加' }))
    await user.click(screen.getByRole('button', { name: 'トースト追加' }))
    expect(screen.getAllByText('メッセージ')).toHaveLength(2)
  })

  test('閉じるボタンを押すと即座に消える', async () => {
    const user = userEvent.setup({ advanceTimers: jest.advanceTimersByTime })
    render(
      <Wrapper>
        <TriggerButton message="手動で閉じる" variant="info" />
      </Wrapper>,
    )
    await user.click(screen.getByRole('button', { name: 'トースト追加' }))
    await user.click(screen.getByRole('button', { name: '通知を閉じる' }))
    expect(screen.queryByText('手動で閉じる')).not.toBeInTheDocument()
  })

  test('通知領域に aria-live="polite" が設定されている', () => {
    render(<Wrapper><div /></Wrapper>)
    expect(
      screen.getByRole('region', { name: '通知' }),
    ).toHaveAttribute('aria-live', 'polite')
  })

  test('複数トーストのうち閉じるボタンを押したものだけ消える', async () => {
    const user = userEvent.setup({ advanceTimers: jest.advanceTimersByTime })
    render(
      <Wrapper>
        <TriggerButton message="トースト1" variant="success" />
        <TriggerButton message="トースト2" variant="error" />
      </Wrapper>,
    )
    const addButtons = screen.getAllByRole('button', { name: 'トースト追加' })
    await user.click(addButtons[0])
    await user.click(addButtons[1])

    const closeButtons = screen.getAllByRole('button', { name: '通知を閉じる' })
    await user.click(closeButtons[0])  // トースト1だけ閉じる

    expect(screen.queryByText('トースト1')).not.toBeInTheDocument()
    expect(screen.getByText('トースト2')).toBeInTheDocument()
  })

  test('3秒経過したトーストだけ消える', async () => {
    const user = userEvent.setup({ advanceTimers: jest.advanceTimersByTime })
    render(
      <Wrapper>
        <TriggerButton message="先に追加" variant="success" />
        <TriggerButton message="後から追加" variant="info" />
      </Wrapper>,
    )
    await user.click(screen.getAllByRole('button', { name: 'トースト追加' })[0])

    await act(async () => { jest.advanceTimersByTime(1_000) })  // 1秒経過

    await user.click(screen.getAllByRole('button', { name: 'トースト追加' })[1])

    await act(async () => { jest.advanceTimersByTime(2_000) })  // さらに2秒（合計3秒）

    expect(screen.queryByText('先に追加')).not.toBeInTheDocument()   // 合計3秒 → 消える
    expect(screen.getByText('後から追加')).toBeInTheDocument()        // 1秒しか経っていない → 残る
  })

7Phase 4 連携メモ — SSE と useToast の接続

Phase 4 で実装する SSE クライアントから addToast を呼ぶ実装イメージ。 本イシューのフックをそのまま使える。

Phase 4 実装イメージ（SSE クライアントコンポーネント） tsx 
'use client'

import { useEffect } from 'react'
import { useToast } from './_components/ToastContext'

export function SseListener() {
  const { addToast } = useToast()

  useEffect(() => {
    const es = new EventSource('/api/sse/events')

    es.addEventListener('batch-completed', (e) => {
      const data = JSON.parse(e.data)
      const ok   = data.status === 'COMPLETED'
      addToast(
        ok ? 'バッチが完了しました' : 'バッチが失敗しました',
        ok ? 'success'           : 'error',
      )
    })

    return () => es.close()
  }, [addToast])

  return null
}
🔮
本番化向け改善案 — エラーを assertive で読み上げる WCAG 2.1 SC 4.1.3「ステータスメッセージ」に完全準拠するには、 error トーストを aria-live="assertive" の別リージョンで管理する。 Toaster を polite / assertive の 2 つのリージョンに分け、 toasts.filter(t => t.variant !== 'error') と toasts.filter(t => t.variant === 'error') にそれぞれ流す実装にすることで対応できる。

Q&AuseCallback 深掘り

ToastContext.tsx の useCallback と setState 関数渡しについて、対話形式で掘り下げる。

Q
addToast や removeToast で useCallback を使っている理由は、 プロバイダーコンポーネントが更新されるたびに関数が再作成されるのを防止するためだったっけ？
A

そのとおりです。ただ、このコードの場合はもう一段深い理由があります。

addToast / removeToast は value={{}} でコンテキストに渡されます。

<ToastContext value={{ toasts, addToast, removeToast }}>

この value オブジェクトは毎レンダリングで新しく作られます。 もし addToast が毎回新しい関数になっていると、toasts の変化と無関係な場面でも 「値が変わった」とみなされ、コンテキストを購読しているすべての子コンポーネントが再レンダリングされます。

useCallback で関数参照を固定することで、 toasts が変わったときだけ子が再レンダリングされる状態に近づけています。

Q
なんで setToasts((prev) => ...) と関数形式で書くと、 toasts を依存配列に入れなくて済むようになるの？
A

setState の2つの呼び方の違いから説明します。

// 値渡し
setToasts([...toasts, newToast])
//          ^^^^^^
//          addToast が作られた時点でキャプチャされた toasts

// 関数渡し
setToasts((prev) => [...prev, newToast])
//          ^^^^
//          React が「今この瞬間の最新値」を引数として渡してくれる

useCallback の依存配列は「関数の中で参照している外部変数」を列挙するものです。 値渡しでは toasts という外部変数を参照しているため [toasts] が必要になります。 関数渡しでは prev は React から受け取る引数であり外部変数ではないため、依存配列を [] にできます。

Q
まだわかんない。setToasts([...toasts, newToast]) と書くと、 toasts に代入されるのは addToast が作られた時点の値で固定されてしまうの？ ステートの toasts が更新されたときに反映されないの？
A

そこがポイントです。useCallback に [] を渡すと関数が一度しか作られないことが問題になります。

// 1回目のレンダリング
toasts = []
addToast が作られる → この時点の toasts（= []）を記憶する

addToast("A") を呼ぶ
  setToasts([...toasts, A])
           ↑ 記憶していた [] を使う
  → state が [A] になる

// 2回目のレンダリング
toasts = [A]
でも addToast は [] のまま再作成されない！
→ addToast の中の toasts はまだ [] のまま

addToast("B") を呼ぶ
  setToasts([...toasts, B])
           ↑ 古い [] を使う（[A] ではない）
  → state が [B] になる  ← [A, B] にならない！

これを stale closure（古いクロージャ）と呼びます。

関数渡しなら prev に React が最新の state を注入してくれるため、クロージャに古い値が閉じ込められていても無関係です。

addToast("B") を呼ぶ
  setToasts(prev => [...prev, B])
                    ↑ React が最新の [A] を渡してくれる
  → state が [A, B] になる ✅
Q

なるほど。つまりこういうこと？

  • setToasts([...toasts, ...]) と書いた場合 → 依存配列に [toasts] が必要 → toasts が更新されるたびに addToast が再作成される → 子コンポーネントの不要な再レンダリングが生じる
  • setToasts((prev) => [...]) と書いた場合 → 依存配列は [] でよい → 関数が再作成されない → 子コンポーネントの不要な再レンダリングを防止できる
A

完璧です。図にまとめるとこうなります。

値渡し: setToasts([...toasts, newToast])
  ↓
依存配列に [toasts] が必要
  ↓
toasts が更新されるたびに addToast が再作成される
  ↓
value={{ toasts, addToast, removeToast }} が変わる
  ↓
コンテキストを購読している子コンポーネントが全部再レンダリング ❌


関数渡し: setToasts(prev => [...prev, newToast])
  ↓
依存配列は [] でよい
  ↓
addToast は一度しか作られない（参照が変わらない）
  ↓
toasts が変わったときだけ子が再レンダリング ✅

useState の関数渡しは「stale closure を避けつつ useCallback の最適化を活かす」定番のパターンです。 今後 useReducer や他の useState を扱うときも同じ考え方が使えます。
