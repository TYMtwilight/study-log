# AUTH_SECRET と Google OAuth の仕組み

---

## 全体の流れ

Google OAuth ログインは「Google が本人確認をする」「アプリがセッションを管理する」という 2 段階に分かれています。

---

### 段階 1 — Google が本人確認する（`AUTH_GOOGLE_ID` / `AUTH_GOOGLE_SECRET` の出番）

```
ユーザーが「Google でログイン」を押す
        ↓
Auth.js が Google の認証画面へリダイレクト
        ↓
ユーザーが Google アカウントでログイン・許可する
        ↓
Google が Auth.js へ「この人は本物です」と通知する
   （このとき AUTH_GOOGLE_ID / AUTH_GOOGLE_SECRET で
     「通知の送り先が正しいアプリか」を Google が確認する）
```

ここまでが Google Cloud との通信です。`AUTH_SECRET` はここには登場しません。

---

### 段階 2 — アプリがセッションを管理する（`AUTH_SECRET` の出番）

Google から「本物です」と通知を受けた後、Auth.js は自分のアプリ内でログイン状態を管理する必要があります。

```
Google から「本物です」と通知を受ける
        ↓
Auth.js が JWT（ログイン証明書）を作る
        ↓
AUTH_SECRET を使って JWT に「署名」する
        ↓
署名済み JWT をブラウザの Cookie に保存する
        ↓
次回以降のアクセス時、Cookie の JWT を AUTH_SECRET で検証する
→ 署名が正しければ「ログイン済み」と判断する
```

---

### 3 つの環境変数の役割まとめ

```
AUTH_GOOGLE_ID      → Google に「このアプリです」と名乗るための ID
AUTH_GOOGLE_SECRET  → Google に「このアプリです」と証明するための合言葉
AUTH_SECRET         → 自分のアプリ内で JWT を改ざんから守るための秘密の値
                      （Google には一切送られない）
```

---

## JWT の署名の仕組み

### JWT の構造

Auth.js がブラウザに渡す JWT は 3 つのパーツでできています。

```
ヘッダー.ペイロード.署名
```

具体的にはこういう内容です。

```
ペイロード（本文）:
{
  "userId": "abc123",
  "name": "Hiroki",
  "email": "hiroki@example.com"
}
```

---

### 署名の作り方

Auth.js はログイン成功時に、次の計算をします。

```
署名 = ハッシュ関数( ペイロードの内容 + AUTH_SECRET )
```

**ハッシュ関数** とは「同じ入力からは必ず同じ出力が得られるが、出力から入力は逆算できない」計算のことです。

例えばこうなります。

```
ハッシュ関数( "userId=abc123..." + "my-secret-key" )
→ "a3f8c2d1e9b7..."  ← これが署名
```

この署名をペイロードにくっつけてブラウザへ渡します。

```
JWT = ペイロード + 署名"a3f8c2d1e9b7..."
```

---

### 攻撃者が JWT を書き換えようとしたとき

攻撃者がペイロードを書き換えて別人になりすまそうとします。

```
# 攻撃者が書き換えたペイロード
{
  "userId": "admin999",   ← 書き換えた
  "name": "Admin",        ← 書き換えた
  "email": "..."
}
```

しかし署名は元のままです（攻撃者は `AUTH_SECRET` を知らないので新しい署名を作れません）。

```
書き換え後のペイロード + 古い署名"a3f8c2d1e9b7..."
```

サーバーは受け取ったとき、手元の `AUTH_SECRET` で再計算します。

```
ハッシュ関数( "userId=admin999..." + "my-secret-key" )
→ "z9q2w8r5t4m1..."  ← 全然違う値になる
```

元の署名 `a3f8c2d1e9b7...` と一致しないので「改ざんされている」と検知できます。

---

### なぜ AUTH_SECRET を秘密にする必要があるのか

```
AUTH_SECRET を知っている → 正しい署名を作れる（サーバーだけ）
AUTH_SECRET を知らない  → 署名を作れない（攻撃者）

署名が一致する   → 本物の JWT
署名が一致しない → 改ざんされた JWT
```

`AUTH_SECRET` が漏れると、攻撃者が任意のペイロードに正しい署名を付けられるようになります。つまり「誰でも任意のユーザーになりすませる」状態になるため、絶対に公開してはいけません。
